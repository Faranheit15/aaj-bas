# Scripts

This directory holds repository check scripts and the content commands.

- `check-agents-md-size.sh` — guards the agent instruction files against silent Codex truncation.
- `check-package-manager.sh` — enforces `AGENTS.md` section 8.
- `validate-edition.ts` — `bun run content:validate`. It reads every `*.json` in `content/editions/` (or the paths named on the command line), hands the text to the rule engine in `packages/domain`, prints a report, and exits non-zero on a blocking finding. `--json` writes a machine-readable report to stdout; `--publish` also treats a not-publishable edition as fatal, and is what the `deploy-web` job runs over the staged editions in `apps/web/dist/content/` before uploading them. The file deliberately holds no rule, severity, or threshold: what is wrong with an edition is a domain question, and this script exists only because the domain package must not touch a filesystem.
- `validate-sources.ts` — `bun run sources:validate`. It reads `content/sources.yml` (or the paths named on the command line), parses the YAML, hands the parsed value to the source-registry rules in `packages/domain`, prints a report, and exits non-zero on a blocking finding. `--json` writes a machine-readable report to stdout. It differs from `validate-edition.ts` in exactly one way, recorded in ADR-0012: the validation entry point takes a parsed value rather than text, because `Bun.YAML.parse` is the parser and `Bun` is undefined under Vitest, so the parse has to live in the command. A missing registry and a registry declaring no entries both exit 3 rather than 1 — section 37 distinguishes "nothing was checked" from "something is wrong" — while YAML that does not parse is a blocking failure, because a file this command could not read is not a file that held nothing. There is no `--force` and no per-rule mute, and there must never be one: every rule here is either the record of a human having read a publisher's terms or the classification of a host something will later fetch, and a flag silencing either is the flag that publishes an unreviewed source. That absence is a tested fact rather than a paragraph: `packages/domain/src/source-registry/command.test.ts` spawns this command and asserts each of its exit codes, `--force` among them. It lives there because `scripts/` is not a workspace, so `bun run test` does not reach a test file in this directory — anything written here would never run.
- `stage-content.ts` — `bun run content:stage`. It validates every edition, then copies the ones a build may carry into `apps/web/public/content/editions/` and writes the pointer `apps/web/public/content/latest.json`. A blocking finding stops it and stages nothing, so a broken edition fails the build instead of quietly shipping a shorter one. `--include-sample-data` also stages editions the validator flagged as invented content, which is how `bun run dev` has anything to render; it relaxes who may see sample data and nothing about correctness, so a genuinely broken edition is still withheld in that mode. It runs from `apps/web`'s own `dev` and `build` scripts rather than from `check`, because the artifact belongs to a build.

Two things `stage-content.ts` does are load-bearing. It deletes every staged `*.json` the current run will not write, because `apps/web/public/` is an ordinary source directory that nothing else clears — `vite build` empties `dist/`, not `public/` — so without it a `dev` run's sample edition would ship in the next production build. And it copies edition files byte for byte rather than re-serialising them, so the deployed file is identical to the one a human reviewed and no formatter or JSON round trip can alter published content on its way to a reader. The staged directory is git-ignored for the same reason: it is a build artifact, and a committed copy would be a second version of every edition that can disagree with `content/`.

`scripts/` is now type-checked. `bun run typecheck` ends with `bunx tsc --noEmit -p scripts/tsconfig.json`; before `validate-edition.ts` there was no TypeScript here and the directory was not covered. `tsconfig.json` extends the repository base with `"types": []`, and `bun-runtime.d.ts` declares the handful of Bun and `process` members these scripts actually call. The declarations are hand-written because the repository installs neither `@types/node` nor `bun-types`: a large ambient surface for one small script is the kind of dependency section 11 asks to avoid, and the same call was already made in `packages/test-fixtures`. The risk is a declaration that type-checks but does not exist, and the safety net is that `bun run content:validate` and `bun run build` — which stages content — both run in the blocking suite, so a wrong declaration fails on the next run. Verify a member exists at runtime (`bun -e`) before declaring it.

The repository still does not fetch sources, generate summaries, or publish editions. This directory is reserved for that deterministic content processing when it arrives.
